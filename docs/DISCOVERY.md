## 1. 技术判断：这个项目和你现有站点的根本区别

### 1.1 驱动模型的差异（最重要的一条）

`Celestial-Web` 是 **scrub（擦洗）模型**：

```
滚动位置  ──(纯函数)──▶  进度 p  ──(纯函数)──▶  画面
```

它的铁律是「动画量是滚动位置的纯函数，页面滚多少动多少，手一停动画就停」。它甚至用 CSS 强制禁用了全站所有 `transition` / `animation`。

**WemZone 要的是另一种模型**，你描述的四件事和 scrub 直接冲突：

| 你的要求 | 为什么 scrub 做不到 |
|---|---|
| 微弱滚动 → 位移一下再弹回（果冻） | 需要「弹簧物理 + 回正」，scrub 只会停在滚到的位置 |
| 一次滚动只前进一个区，滚多少都一样 | 需要「意图识别 + 状态机 + 输入锁定」 |
| 切换时先慢后快再慢 | 需要「按时间走的补间」，scrub 是位置驱动 |
| 无滚动时摄像机持续轻微晃动 | 需要「常驻时间驱动的动画」，正是它明令禁止的 |

所以 WemZone 的模型是：

```
滚轮/触摸事件  ──▶  意图识别  ──▶  状态机  ──▶  目标位置
                                    │
                         弹簧/补间物理  ──▶  摄像机状态(位置/旋转/FOV)
                                    │
                              纯函数映射  ──▶  画面
```

**「纯函数映射」那一层完全继承 Celestial-Web 的写法**（`ease.ts` 直接拿来用），
只是把驱动源从 `window.scrollY` 换成「摄像机状态」。`scroll.ts` 里除了
`measure()` 的进度公式之外的部分（监听合并、读写分离、空闲检测、`chase`、
reduced-motion）全部可以移植。

### 1.2 空间模型：一块真的 3D 平面

内容块按「世界坐标」摆放，向下延伸、左右交替：

```
锚点 A_i = (x_i, y_i, z_i)
  x_i 交替 ±L（或沿一条轻微弯曲的脊线）
  y_i = -i · VERTICAL_SPACING
  z_i = 该区自己的「摄像机距离」

摄像机沿一条 Catmull-Rom 样条穿过这些锚点（保证「曲线平滑连接」）
```

**CSS 实现的关键技巧**（决定了这个方案能不能便宜地跑起来）：

```
#viewport { perspective: P; perspective-origin: cx cy; }   ← 相机平移 = 移动消失点
#world    { transform: translateZ(cz) rotateX(rx) rotateY(ry) rotateZ(rz); }
   各 section 用 absolute 摆在自己的世界坐标上
```

这样每帧只有 **两次写入**（`perspective-origin` 和 `#world` 的 `transform`），
section 自身的 transform 是静态的。这比「逐元素重算」便宜一个数量级。

> 注意：`perspective-origin` 是唯一能产生真实视差的做法。只 `translate` 子元素
> 不会改变消失点，那是整体平移、没有近大远小。

**每个区不同的「摄像机距离」**：给该 section 一个 `translateZ(z_i)`，
再用 `scale(P / (P + z_i))` 反向补偿，即可做到「距离变了但内容视觉大小不变」，
只有透视压缩感和与其它元素的视差变了。这正是你说的
「摄像机到内容面的距离可以改变，但内容大小要相应改变来确保视觉效果」。

### 1.3 四个子系统

| 子系统 | 职责 | 复用 |
|---|---|---|

## 2. 技术栈建议

### 推荐：**Vue 3 + Vite + TypeScript + Tailwind CSS v4，纯静态构建**

理由，按权重排序：

1. **引擎应该是框架无关的 vanilla TS**。这个项目的核心是命令式动画（每帧读写 transform），
   响应式框架在这里帮不上忙，反而容易引入「一帧改多次状态」的性能陷阱。
   所以：**引擎用纯 TS 写，Vue 只负责渲染 section 和绑定样式。** 这样引擎可单独测试、
   将来换框架也不用重写。
2. **有已验证的同源参考**。`Celestial-Web` 用同一套栈做出了同类站点，代码可以直接搬。
   这比任何理论优势都实在。
3. **静态站 + 文字内容为主** → DOM 比 canvas 合适得多（可选中、可被搜索引擎读、可访问性、
   加新内容只是加一个组件）。
4. Tailwind v4 的 `@tailwindcss/vite` 插件模式（`Celestial-Web` 已在用）足够。

### 明确**不**用的

| 技术 | 为什么不用 |
|---|---|
| **Three.js / WebGL 渲染内容** | 文字进 WebGL 要转纹理或叠 DOM 层，清晰度、可选中、可访问性、可扩展性全面变差。你以后加内容会很难受。 |
| **GSAP ScrollTrigger** | 它是 scrub 模型，和你的交互要求正面冲突。GSAP 的补间/弹簧可以用，但为此引入一整个库不值得——`chase()` 30 行就够。 |
| **Lenis 等平滑滚动库** | 我们要接管滚动，它会打架。 |
| **CSS `animation-timeline: scroll()`** | 跨浏览器还不齐，且它同样是位置驱动。 |
| **Spline / 整站 3D 场景导出** | 内容不可扩展，等于把自己锁死。 |

### 可选（我倾向都不用，列出来供你否决）

- **`@paper-design/shaders`** — 背景的流体 + 像素层，`Celestial-Web` 已在用，**建议继续用**。
- **Theatre.js** — 带 GUI 的动画编辑器，适合调摄像机关键帧。但学习成本 + 体积。
- **GSAP MotionPathPlugin** — 样条运动。我们用 Catmull-Rom 手写 ~40 行即可。

### 运动模糊：这是唯一需要先做原型的风险点

CSS 的 `filter: blur()` 是**各向同性**的，看起来像「失焦」而不是「运动」。真正方向性的
运动模糊有三条路：

| 方案 | 效果 | 成本 |
|---|---|---|
| **A. 各向同性 blur + 沿运动方向轻微拉伸** | 中（高速时够用） | 低，GPU |
| **B. SVG `feGaussianBlur` 各向异性 `stdDeviation="sx sy"`** | 好（真正的方向性） | 中，大区域重光栅化有风险 |
| **C. WebGL 全屏拖影后处理** | 最好 | 高，且要和 DOM 内容层同步 |

**我的建议**：先按 A 做（`blur()` 半径由屏幕空间速度驱动 + 沿运动矢量拉伸 + 一层
方向性拖影叠加层），因为它只在切换途中的约 200ms 峰值出现，且拖影层能掩盖糊感。
原型跑起来后实测性能，不够再上 B。**这个我想尽早做个 A/B 原型给你看效果**，
因为它是全项目最不确定的视觉。

## 3. 主要风险（提前说清楚）

1. **接管滚动的代价。** 「一次滚动只走一个区」意味着不能用原生滚动。
   这会连带影响：浏览器滚动条、`Ctrl+F` 页内查找、浏览器前进/后退、
   打印、键盘导航、以及**触控板的惯性滚动**（macOS/Windows 精密触控板一次滑动
   会产生几十个 wheel 事件，处理不当会一次跳好几个区）。
   缓解：切换途中锁输入；保留语义化 DOM（真标题、真链接）；支持键盘；
   提供「全览模式」作为导航兜底。

2. **手机几乎必然要第二套版式。** 3D 平面 + 左右交替布局在竖屏手机上
   不是「小一点」，是构图被裁掉一大半。`Celestial-Web` 的解法（`viewport.ts`
   一条媒体查询切换两套版式）是对的。我倾向手机走「纵向堆叠 + 同样的背景与风格语言，
   但用原生滚动 + `scroll-snap`」，而不是硬塞 3D。

3. **性能预算。** 大区域 blur + 多层 WebGL 背景 + 每帧写 transform，
   在低端设备上会掉帧。需要一开始就定好：背景渲染分辨率上限、blur 的触发条件、
   以及一个「性能模式」降级档。

### C. 视觉与相机
